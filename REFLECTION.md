# ProjectLens AI — Final Reflection

Building ProjectLens AI taught me how to take an AI-powered frontend application from an initial idea to a complete, deployed product. My goal was to create a practical tool that helps project managers identify risks early and make more informed decisions. Rather than building a generic chatbot, I focused on a structured workflow where users provide project details and receive an actionable risk assessment.

One of the most important technical decisions was using a server-side Next.js API route to communicate with Gemini. This keeps the API key out of the browser and allows the application to request structured JSON responses. I designed the prompt to evaluate project timelines, resources, dependencies, financial concerns, and missing information, while producing consistent risk scores and recommendations. I learned that AI integration is not only about receiving a response; it also requires clear prompt design, predictable output, loading states, and useful error handling.

The hardest part was making the AI integration reliable rather than simply getting a successful response. I had to work through model availability, structured output, and different failure scenarios while ensuring the frontend remained usable. This was challenging because AI responses and external services are less predictable than ordinary application logic. One thing that surprised me was how much work was required around the AI model itself—especially validation, error handling, and testing—to turn a simple API call into a dependable user experience.

Testing and accessibility were also significant parts of the project. I implemented automated tests for the dashboard, analysis page, report component, severity logic, and API error scenarios. The final test suite passed all 17 tests, and the latest coverage run achieved 94.23% statement and line coverage. I also improved color contrast, keyboard navigation, form labels, and responsive layouts. Lighthouse testing helped me identify issues and verify improvements, with the latest mobile audit achieving a performance score of 86 and an accessibility score of 100.

Deployment introduced another important learning experience. I connected the GitHub repository to Vercel, configured the Gemini environment variable securely, and verified the live application using a fictional project. I also documented a deployment checklist, rollback approach, and monitoring plan. This helped me understand that shipping software involves more than writing code: it requires verification, maintainability, and a plan for handling failures.

If I were to approach the project differently, I would define the structured response contract and test failure scenarios earlier in development. I would also plan accessibility checks from the beginning rather than treating them mainly as final polish. These changes would reduce rework and make the application easier to maintain as it grows.

The main limitation of the current version is that analyses are not persisted, and the dashboard uses demonstration data rather than a real project portfolio. If I continued developing the product, I would prioritize saved analyses, authentication, historical risk tracking, stronger runtime validation, and automated monitoring. Overall, this capstone strengthened my confidence in building, testing, and deploying a complete AI application, while showing me the importance of keeping the product scope focused and delivering a reliable end-to-end experience.
